Anda adalah senior software architect dan technical writer.

Tugas Anda adalah menganalisis seluruh codebase aplikasi ini dan membuat atau
memperbarui file dokumentasi `APPLICATION_CONTEXT.md` pada setiap aplikasi
yang memiliki context terpisah:

- `backend/APPLICATION_CONTEXT.md`
- `frontend/APPLICATION_CONTEXT.md`

Setiap file menjadi **single source of truth** untuk memahami boundary
aplikasinya masing-masing, baik oleh developer baru, software engineer, AI
coding agent, QA, maupun stakeholder teknis. Jika perubahan menyentuh
frontend dan backend, perbarui kedua file dengan informasi yang relevan dan
konsisten.

## Tujuan

Jangan membuat dokumentasi berdasarkan asumsi atau template generik.

Sebelum menulis dokumentasi, lakukan analisis terhadap repository secara
menyeluruh. Gunakan source code, konfigurasi, database schema/migration, API
routes, models/entities, services, tests, deployment configuration, dan
dokumentasi yang sudah tersedia sebagai sumber utama.

Jika repository memiliki beberapa aplikasi, analisis setiap aplikasi sebagai
boundary terpisah. Untuk repository ini:

```text
backend/  -> aplikasi Go, Gin, GORM, dan database
frontend/ -> aplikasi React, TypeScript, Vite, dan API client
```

Jangan menganggap frontend memiliki akses langsung ke database. Catat
integrasi antara frontend dan backend secara konsisten pada kedua context.

Jika terdapat informasi yang tidak dapat dipastikan dari codebase, tandai secara eksplisit sebagai:

`[UNKNOWN]`

Jangan mengarang informasi.

Jika terdapat dokumentasi lama yang bertentangan dengan implementasi aktual, prioritaskan **implementasi aktual di codebase**, lalu catat discrepancy tersebut di bagian `Known Inconsistencies`.

# 2. Buat atau perbarui APPLICATION_CONTEXT.md

Buat atau perbarui file context pada boundary aplikasi yang relevan. Untuk
repository ini, gunakan:

```text
backend/APPLICATION_CONTEXT.md
frontend/APPLICATION_CONTEXT.md
```

Informasi yang hanya dimiliki backend, seperti model database, migration,
seeder, dan middleware server, dicatat di context backend. Informasi yang
hanya dimiliki frontend, seperti komponen React, route SPA, API wrapper, dan
state UI, dicatat di context frontend. Informasi integrasi antar aplikasi
harus konsisten di kedua file.

Gunakan struktur berikut pada masing-masing file.

# Dokumentation Rules

Ikuti aturan berikut:

1. Jangan mengarang informasi.
2. Jangan memasukkan secret atau credential.
3. Bedakan fakta, inference, dan unknown.
4. Jika informasi tidak ditemukan, tulis `[UNKNOWN]`.
5. Gunakan implementation aktual sebagai source of truth.
6. Jangan mengubah source code hanya untuk membuat dokumentasi.
7. Jangan membuat diagram yang tidak sesuai dengan implementation.
8. Jangan menyalin source code dalam jumlah besar.
9. Fokus pada informasi yang membantu manusia dan AI memahami sistem.
10. Hindari dokumentasi yang terlalu verbose terhadap detail implementation yang tidak penting.
11. Gunakan bahasa yang jelas dan teknis.
12. Gunakan Markdown.
13. Gunakan Mermaid jika diagram dapat memperjelas architecture, workflow, ERD, atau state machine.
14. Semua command yang ditulis harus diverifikasi dari repository.
15. Jangan mencantumkan credential aktual meskipun ditemukan di repository.
16. Jangan menghapus atau mengubah dokumentasi existing.
17. Hanya buat atau update `APPLICATION_CONTEXT.md` yang relevan pada
    `backend/` dan/atau `frontend/`. Jangan mengubah source code atau file lain.

# Proses Kerja

Ikuti proses berikut secara berurutan:

### Step 1 — Explore

Scan repository dan identifikasi architecture, modules, dependencies, database, API, integrations, configuration, tests, dan deployment.

Jika terdapat lebih dari satu aplikasi, buat catatan terpisah untuk backend dan
frontend. Identifikasi juga boundary komunikasi API di antara keduanya.

### Step 2 — Verify

Cross-check informasi antara source code, configuration, tests, schema, dan existing documentation.

### Step 3 — Map

Buat mental model:

```text
Users
 ↓
Features
 ↓
Modules
 ↓
Services
 ↓
Data
 ↓
Infrastructure
 ↓
External Dependencies
```

### Step 4 — Document

Buat atau perbarui `backend/APPLICATION_CONTEXT.md` dan/atau
`frontend/APPLICATION_CONTEXT.md` berdasarkan hasil analisis. Update hanya
context yang terkena perubahan, tetapi perbarui keduanya jika kontrak
integrasi berubah.

### Step 5 — Self Review

Setelah file selesai, review kembali dan pastikan:

- Tidak ada informasi yang diada-adakan.
- Tidak ada secret.
- Tidak ada architectural claim tanpa evidence.
- Semua module utama tercakup.
- Business rules penting tercakup.
- Critical workflows tercakup.
- Database/domain model tercakup.
- API/integration penting tercakup.
- Developer setup dapat diikuti.
- AI agent dapat memahami batasan architecture.
- `[UNKNOWN]` digunakan jika informasi memang tidak dapat diverifikasi.

### Step 6 — Final Report

Setelah selesai, berikan ringkasan singkat:

```text
Created or updated:
backend/APPLICATION_CONTEXT.md
frontend/APPLICATION_CONTEXT.md

Repository analyzed:
...

Main modules identified:
...

Main integrations identified:
...

Important unknowns:
...

Potential documentation gaps:
...
```

Jangan mengubah source code atau file lain selain `APPLICATION_CONTEXT.md` yang
relevan pada boundary aplikasi tersebut.
